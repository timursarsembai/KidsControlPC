# Выпуск релиза агента

Как собрать обе сборки и выложить релиз, никого при этом не сломав.

Про подготовку машины (Node, Visual Studio Build Tools, NSIS) — в
[BUILD-AGENT.md](BUILD-AGENT.md). Здесь только сам выпуск.

---

## Почему порядок важен

Агент обновляется сам: раз в два часа он смотрит **последний релиз** этого
репозитория и скачивает оттуда установщик. Из этого следуют две вещи.

**Релиз раскатывается на всех, у кого стоит агент.** Не «предлагается» —
скачивается и ставится тихо. Ошибка в релизе доедет до каждого детского ПК за
пару часов.

**Сборки различаются только сервером, к которому ходят.** До версии 1.1.110
обе назывались `KidsControlAgent_Setup.exe`, и агент брал файл по имени. То
есть выложенная сборка для своего сервера увела бы боевых пользователей на
`kidscontrol.kz`, где их устройств нет, а боевая сборка — увела бы своего
агента в Firebase. Теперь имена разные:

| сборка | файл | к какому серверу ходит |
|---|---|---|
| боевая | `KidsControlAgent_Setup.exe` | Firebase |
| своя | `KidsControlAgent_SelfHosted_Setup.exe` | `api.kidscontrol.kz` |

Один релиз может нести оба файла — каждый агент возьмёт свой.

> **Осталось одно окно.** Агенты **версии 1.1.109 и старше** — в том числе тот,
> что сейчас стоит на вашем ноутбуке от своего сервера, — про новое имя не
> знают и по-прежнему ищут `KidsControlAgent_Setup.exe`. Если выложить релиз
> раньше, чем обновить ноутбук вручную, ноутбук скачает боевую сборку и уйдёт
> в Firebase. Поэтому шаг 2 идёт до шага 4.

## 1. Взять код

На домашнем ПК с Windows, в PowerShell:

```powershell
cd C:\путь\к\KidsControlPC
git fetch origin
git checkout selfhosted
git pull
```

Проверьте, что версия та, которую выпускаете:

```powershell
node -p "require('./agent/package.json').version"
```

Должно быть `1.1.110`. Если нет — версию поднимают в трёх местах:
`agent/package.json`, `agent/package-lock.json` и запасное значение в
`agent/src/config.js`.

> **Почему `selfhosted`, а не `master`.** Все правки агента — устойчивость к
> нехватке памяти, быстрое определение выключения, разные имена установщиков —
> лежат в этой ветке; `master` их не содержит. Код агента общий для обеих
> сборок, Firebase-часть в нём не менялась, так что боевой установщик отсюда
> собирается корректно.
>
> Расхождение веток при этом растёт, и когда-то его придётся закрыть: либо
> влить `selfhosted` в `master`, либо перенести туда одни лишь правки агента.
> Это отдельное решение — в `master` без вашего слова ничего не уходит.

## 2. Своя сборка — и сразу на ноутбук

```powershell
cd agent
npm ci
$env:KIDSCONTROL_BACKEND = "selfhosted"
npm run build
```

Получится `agent\dist\KidsControlAgent_SelfHosted_Setup.exe`.

**Поставьте его на ноутбук прямо сейчас, до выпуска релиза.** Ставить можно
поверх — привязка, правила и история сохранятся. После установки агент начнёт
искать обновления под своим именем, и релиз ему больше не страшен.

Проверьте в панели: устройство «Онлайн», в карточке версия `v1.1.110`.

---

## 3. Боевая сборка

В том же окне PowerShell переменную надо снять — иначе соберётся вторая копия
своей сборки:

```powershell
Remove-Item Env:\KIDSCONTROL_BACKEND
npm run build
```

Получится `agent\dist\KidsControlAgent_Setup.exe`.

> **Проверьте, что собралась именно боевая сборка.** Признак — имя файла: оно
> берётся из того же значения, что и адрес сервера, так что подделать его
> сборка не может.
>
> ```powershell
> Get-ChildItem agent\dist\*Setup.exe | Select-Object Name, LastWriteTime
> ```
>
> Только что изменённым должен оказаться `KidsControlAgent_Setup.exe`. Если
> обновился `KidsControlAgent_SelfHosted_Setup.exe` — переменная осталась в
> окружении: закройте PowerShell, откройте заново, повторите шаг с `npm ci` и
> соберите снова.
>
> Искать в сборке адрес `api.kidscontrol.kz` бесполезно: он есть в обеих,
> потому что объявлен в конфиге безусловно, а выбирается уже на ходу.

## 4. Релиз на GitHub

```powershell
git tag v1.1.110
git push origin v1.1.110
```

Дальше на [странице релизов](https://github.com/timursarsembai/KidsControlPC/releases):

1. **Draft a new release**, тег `v1.1.110`.
2. Приложить **оба** файла: `KidsControlAgent_Setup.exe` и
   `KidsControlAgent_SelfHosted_Setup.exe`.
3. Описание — что изменилось (см. ниже).
4. **Publish release.**

Как только релиз опубликован, он становится `latest`, и агенты начнут его
забирать в течение двух часов.

---

## 5. Убедиться, что доехало

Через час-другой в панели у устройства должна смениться версия. Если нужно
раньше — в разделе питания есть принудительное обновление.

Если что-то пошло не так, самое быстрое лечение — **снять релиз с публикации**
(Edit release → Set as pre-release). Тогда `latest` снова укажет на прошлый, и
агенты перестанут его тянуть. Уже обновившиеся откатятся только установкой
старого установщика вручную.

---

## Что вошло в 1.1.110

Для описания релиза:

- Профили детей: устройства группируются по ребёнку, у одного ребёнка может
  быть несколько компьютеров.
- Выключение компьютера видно родителю за секунды, а не за три минуты; при
  выключении командой из панели — сразу.
- Агент устойчивее на компьютерах с малой памятью: тяжёлые проверки больше не
  наслаиваются друг на друга, сбой сети не роняет службу, при утечке памяти
  агент перезапускается сам.
- Список установленных программ больше не теряется целиком из-за одной длинной
  записи в реестре.

## Чего не делать

**Не выкладывать один установщик под чужим именем.** Имя файла — единственное,
по чему агент отличает свою сборку от чужой.

**Не выпускать релиз, не обновив свой ноутбук** (шаг 2). Пока на нём агент
1.1.109, он возьмёт из релиза боевую сборку.

**Не собирать боевую сборку в окне, где стоял `KIDSCONTROL_BACKEND`.**
Проверка из шага 3 существует ровно для этого случая.

**Не удалять прошлые релизы.** Агенты, не успевшие обновиться, ищут `latest`;
удаление старых ничего не чинит, а откатываться будет некуда.
