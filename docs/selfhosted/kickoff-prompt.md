# Стартовый промпт для Claude Code на сервере

Скопировать всё, что ниже разделителя, и отдать Claude Code первым сообщением.

---

## Контекст

Проект **KidsControlPC** — родительский контроль: агент на Windows-ПК ребёнка,
веб-панель родителя, десктопное приложение на Electron, бэкенд на Firebase.
Репозиторий: https://github.com/timursarsembai/KidsControlPC

Сейчас всё завязано на Firebase (проект `kidscontrolpc`): Firestore, Auth,
Cloud Functions, Storage, Hosting. Данные физически лежат в дата-центрах Google
за пределами Казахстана.

**Задача:** построить自-hosted бэкенд на этом сервере, чтобы персональные данные
хранились на территории РК. Причина не техническая, а юридическая: закон РК
«О персональных данных и их защите» № 94-V, статья 12 требует хранить персональные
данные граждан РК на территории Казахстана. Данные здесь чувствительные — это дети:
активность, посещённые сайты, скриншоты, переписка.

Firebase-версия продолжает работать всё время миграции, её ломать нельзя.

## Принятые архитектурные решения

**Одна кодовая база, не форк.** Работать в ветке `selfhosted`. Новый бэкенд
реализуется за существующим слоем репозиториев `shared/firebase/*.repo.js` —
это готовый шов между данными и UI. Клиенты переключаются конфигом. После
завершения миграции реализация Firebase просто удаляется. Форк отвергнут
сознательно: разработчик один, два дерева означают чинить каждый баг дважды.

**Целевой стек:**

| Сейчас | Станет |
|---|---|
| Firestore | PostgreSQL |
| `onSnapshot` | WebSocket |
| Firebase Auth | свой JWT; у агента — токен устройства |
| Cloud Functions | Node API (логику переносить, не переписывать) |
| Firebase Storage | MinIO или том на диске |
| Firebase Hosting | существующий Nginx Proxy Manager |

**Объём первой версии — только ядро:** устройства, привязка, правила, блокировки,
активность. Чат, скриншоты, приглашения второго родителя и верификация почты —
отложены. Родительский контроль без чата работает, чат без блокировок — нет.

## Первая задача: НЕ писать код

Сначала снять инвентарь сервера и написать план. Конкретно выяснить:

- версии Docker и compose, какие контейнеры уже запущены, какие порты заняты;
- как устроен Nginx Proxy Manager: домены, сертификаты, схема проксирования;
- ресурсы: CPU, RAM, диск, сколько реально свободно;
- есть ли уже PostgreSQL — переиспользовать или поднимать отдельный;
- как устроены бэкапы существующих проектов;
- роль wg-easy: сервер за VPN или смотрит наружу;
- ОС, ядро, файрвол.

Затем предложить письменно: схему БД, поверхность API, протокол realtime,
раскладку контейнеров, порядок деплоя, план миграции данных из Firestore.

Обсудить план с владельцем до начала реализации.

## Жёсткие ограничения

- **Не трогать и не перезапускать существующие контейнеры и проекты.** На сервере
  работают другие боевые сервисы.
- **Не менять ничего в живом Firebase-проекте.**
- Всё новое — отдельный compose-стек, своя сеть, непересекающиеся порты.
- Коммиты в ветку `selfhosted`. В `master` не пушить без явного разрешения.
- Спрашивать перед любым необратимым действием.
- Секреты — в `.env`, не в репозиторий. Проверять, что в коммит не попало лишнее.

## Знание, купленное дорогой ценой — не потерять при переписывании

Это выяснено отладкой на живых устройствах, повторно наступать не нужно:

1. **Агент упакован через `pkg` и работает на Node.js 18.5.** В этой сборке
   `undici` и глобальный `fetch` не работают. Использовать модуль `https` напрямую
   или `node-fetch` v2. На этом уже сгорели: Cloud Functions вызываются через
   голый `https.request`, а `@firebase/auth` втягивал `undici` и молча ронял
   авторизацию — лечилось подменой `undici` на шим поверх `node-fetch` при сборке.

2. **Библиотеки телеметрии не должны иметь возможности уронить агента.**
   `Sentry.init()` бросал исключение на уровне модуля и убивал процесс до
   старта — агент не запускался вообще, а установка выглядела успешной.
   Любую инициализацию оборачивать и проверять версию рантайма.

3. **Блокировки обязаны работать без сети.** Правила кешируются на диск и
   применяются из кеша. Планировщик энфорсера навешивать **до** любых сетевых
   вызовов: раньше он стоял в конце инициализации, и зависший сетевой вызов
   оставлял службу «работающей», но ничего не блокирующей.

4. **Не убивать процесс при потере сети.** Раньше три неудачных heartbeat вызывали
   `process.exit(1)`. На Windows 11 с Modern Standby сеть возвращается через
   десятки секунд после пробуждения, и каждый выход из сна превращался в
   самоубийство. Переподключаться, а не умирать.

5. **Windows не шлёт SIGTERM службам.** Обработчик остановки на `SIGTERM` не
   срабатывает никогда. Учитывать при завершении работы.

6. **Права нельзя привязывать к ротируемому секрету.** Было: право на удаление
   сверяло сохранённый токен с текущим токеном устройства. Токен ротируется —
   и старые записи становятся недосягаемыми навсегда. Проверять подписанную
   личность, а не общий секрет.

7. **Логи не должны сами себя вытеснять.** Энфорсер писал полный список правил
   каждые 5 секунд, лог достигал 38 000 строк за часы и уносил всю диагностику
   старта. Писать по изменению состояния.

8. **Установщик не должен удалять службу до того, как убедился, что поставит новую.**
   Тихое обновление делало `sc delete`, затем не могло перезаписать залоченный
   `WinSW.exe` и обрывалось — машина оставалась без агента навсегда.

## С чего начать

```
git clone https://github.com/timursarsembai/KidsControlPC
cd KidsControlPC
git checkout -b selfhosted
```

Прочитать `AGENTS.md`, затем `shared/firebase/` — там весь слой доступа к данным
и, по сути, готовая спецификация того, что должен уметь новый бэкенд.
